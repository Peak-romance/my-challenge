## 3. 问题解决深度（真实缺陷 → 根因 → 修复）

### 问题 1：依赖解析失败（首次 `pip install -r` 即崩）
- **现象**：`ERROR: Could not find a version that satisfies the requirement pydantic-core==2.27.2`。
- **根因**：`requirements.txt` 死锁 `pydantic==2.10.4`，其强约束 `pydantic-core==2.27.2` 在 Python 3.13 没有发布 cp313 轮子。这是**历史版本锁定与当前运行时不兼容**，文档完全未提及。
- **修复**：将 pydantic 升到已验证兼容的 `2.11.9`（保持 pydantic v2 API，对现有代码无破坏），并在行内注释写清原因。原文件已备份为 `requirements.txt.bak`。

### 问题 2：装上了却 `import` 不到（环境错位）
- **现象**：`pip install` 报 `Successfully installed`，但 `python -c "import pydantic"` 报 `ModuleNotFoundError`。
- **根因**：本机存在两个 Python——shell 的 `python` 指向 WorkBuddy 管理的 `3.13.12`，而裸 `pip` 指向另一处 `3.13.14`。`pip install` 把包装进了后者，`python` 用的是前者。
- **修复**：全程统一使用 `python -m pip install`，让 pip 永远指向当前 `python` 的解释器。

### 问题 3：镜像源卡死 / 截断 JSON（网络约束）
- **现象**：一次安装空输出被 SIGTERM，一次报 `JSONDecodeError: Unterminated string`（镜像返回的超长版本清单被截断）。
- **根因**：企业镜像对大依赖树的 simple-index 偶发不稳定；`uvicorn[standard]` 额外引入 watchfiles/uvloop 等可选依赖，进一步放大依赖树与失败面。
- **修复**：① 去掉 `[standard]` 可选依赖；② 依赖分批安装；③ 用工具原生后台任务 + 日志文件运行，避免 `nohup ... &` 被任务框架误杀（这一误杀本身也消耗了一轮时间）。

### 验证（闭环证据）
- `python tools/smoke_test.py` → **通过 91，失败 0**
- `python tools/check_dom_refs.py` → 静态一致性通过
- `node tools/check_js.js` → 14/14 JS 块语法通过
- 真实启动后端：`/api/health=200`，导出 `handover.docx`（37 KB，PK 头）、`handover.pdf`（79 KB，%PDF 头）均为真实有效文件（见 `拿来说明/live/evidence/`）。

## 4. AI 使用反思

- **用得好**：让 AI 快速通读大型代码库（README / seed / router），在几分钟内建立"这是什么项目、真实问题在哪"的判断；由 AI 生成证据抓取脚本（启动后端 + curl + 导出），把"能跑"变成可存档的物证。
- **用得不够 / 应改进**：第一步我直接用裸 `pip`，没有先让 AI 做一个"环境侦探"——核对 `python` 与 `pip` 是否同一解释器、`requirements` 的版本锁是否适配当前 Python。这一步本可省掉**整整一次返工**（约 10 分钟 + 一轮安装尝试）。
- **原则提炼**：真实项目的第一阶段应是"环境对齐检查"，而非"直接动手"。AI 最适合在此阶段做"对齐清单"与"失败模式预判"。

## 5. 与练习（C1–C7）的具体差异清单

1. **需求隐含**：练习给任务书；C8 只给"闲置代码"，需求、验收都要自己定义。
2. **技术栈庞大**：单文件/小项目 → 全栈 + 数据库 + 脚本工具链，任何一环断了整体不可跑。
3. **反馈慢且稀疏**：真实报错不是"第 3 行语法错"，而是"某个版本在 3.13 没轮子"这种需要推理的环境问题。
4. **需自我定义验收**：没有老师给的评分点，必须自己把"可验收"翻译成可量化 AC（见 proposal §5）。
5. **交付物要可独立复现**：练习交代码即可；C8 交的是"证据链"——别人按说明应能复现全绿。

## 6. 改进方案（可落地）

1. **项目交接环境侦探清单**（立即可用）：任何"继承代码"第一步先执行
   ```bash
   where python && where pip && python -m pip --version
   ```
   确认 `python` 与 `pip` 同源，再装依赖；并查 `pip debug --verbose` 确认目标标签（如 cp313）有对应轮子。
2. **依赖用兼容区间替代死锁**：`pydantic>=2.11,<3` 比 `==2.10.4` 更抗版本漂移；关键库锁定**大版本**即可。
3. **一键自检脚本**：新增 `verify.py`/`make check`，把 smoke + dom + js 串成一条命令，把"反馈闭环"自动化，交接人 30 秒知道健康度。
4. **README 补"环境约束"段**：把本次发现的两个 Python、3.13 注意项、免 Docker 启动写进文档，消除"文档声称 vs 真实可跑"的鸿沟。
5. **个人工作法**：做真实项目时，前 10% 时间强制花在"环境侦探"（版本/解释器/网络/权限），再写代码——这 10% 能省掉后面 50% 的返工。

## 8. 复盘给后续同类项目的 3 条铁律

1. **先对齐环境，再写代码。** 解释器、包管理器、运行时版本必须同源可验证。
2. **把"能跑"变成证据。** 自动化测试 + 真实导出的实物文件，比"我试过能跑"可信一万倍。
3. **文档声称 ≠ 真实可跑。** 任何"开箱即用"都要用一条可重跑的命令去证伪，而不是默认相信。
