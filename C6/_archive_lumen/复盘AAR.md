# 复盘报告（After-Action Review, AAR）

> 针对「C6 Web Application」挑战的系统性复盘：目标 → 结果 → 差异根因 → 洞察 → 改进。

---

## 1. 目标回顾

挑战要求：**构建真实可运行的产品，不是 demo**，并交付四类产物（app 链接 / demo / repo 链接 / AI 日志），按五项标准评分：

| 标准 | 权重 | 目标水位 |
| --- | --- | --- |
| productQuality 产品完成度 | 25 | 功能闭环、体验完整 |
| technicalExecution 技术实现 | 20 | 方案合理、工程质量 |
| artifactCompleteness 产物完整性 | 15 | 齐全、可运行、可独立使用 |
| aiUsage AI 使用质量 | 20 | 恰当、有效、可追溯 |
| reflectionQuality 复盘质量 | 20 | 深入、有洞察、有改进 |

## 2. 实际结果

- 交付了一个**全栈技术内容社区「聚光 Lumen」**：注册/登录、发布/编辑/删除文章、信息流（最新/热门/关注）、详情、点赞、收藏、评论、关注、搜索、标签、个人主页。
- 技术栈：Next.js 14 App Router + TypeScript + node:sqlite + Tailwind + react-markdown。
- 产物：`D:/C6` 下含源码、README、AI日志、本复盘、种子脚本；可 `npm install && npm run seed && npm run dev` 直接运行；通过 WorkBuddy 发布获得 app 链接；本地 git 仓库可推送 GitHub。
- 过程中暴露的关键问题：**依赖安装因网络延迟卡死 21 分钟**，经诊断切换国内镜像解决。

## 3. 差异与根因分析

| 预期 | 实际 | 根因 |
| --- | --- | --- |
| 安装 2-3 分钟完成 | 21 分钟无产物 | 默认 registry 约 10s/请求延迟，解析阶段被拖垮 |
| 一次写对导入关系 | 出现 1 处跨模块误导入 | 快速批量生成代码时未严格核对导出位置 |
| 组件纯净 | 差点把原生模块引入客户端 | 工具函数与 DB 逻辑同文件，耦合不清 |

**根因归纳**：
1. **环境假设偏差**：未在一开始就按“用户在中国大陆”这一上下文选择最优镜像，而是先用默认源。
2. **生成速度与校验的平衡**：为赶进度批量写文件，弱化了“写完即核对依赖图”的纪律。
3. **关注点未彻底分离**：`db.ts` 既含连接逻辑又含格式化函数，导致组件面临误引风险。

## 4. 关键洞察

1. **“可运行”优先于“技术炫技”**。在受限环境里，node:sqlite 比 Prisma 更稳健——这正是对 artifactCompleteness（15 分）最友好的取舍。工程打分不只看复杂度，更看“拿到的东西能不能跑起来”。
2. **诊断要先看“有没有在动”**。21 分钟时一个 `du -sh node_modules` 立刻定位到“卡在解析而非下载”，比盲目等待高效得多。可观测性（observability）在排障中价值极高。
3. **架构分层降低 AI 出错面**。把数据访问（models）、连接（db）、格式化（format）、认证（auth）拆开后，即使某一处写错，影响面也被限制在单文件内，便于快速修正。
4. **评分标准本身是需求文档**。五项标准直接映射成任务清单（产品闭环、技术说明、可运行交付、AI 日志、复盘），逐项对齐能显著提升交付命中率。

## 5. 改进方案（可落地）

### 5.1 环境层（立即可做）
- **默认使用就近镜像**：在中国大陆环境，安装前先 `npm config set registry https://registry.npmmirror.com`（或项目级 `.npmrc`），可节省大量无效等待。
- **可观测安装**：用 `npm install --loglevel=http` 或安装进度条，第一时间发现卡点，而非 `tail` 吞掉输出。

### 5.2 工程层
- **严格模块边界**：格式化/纯函数（format.ts）与带副作用的 DB 逻辑（db.ts）必须分离，并在组件层只 import 纯函数。
- **写后即校验**：批量生成后，立即跑一次 `tsc --noEmit` 与 `next build` 的“类型+导入”阶段，把误导入在构建期暴露，而非运行时。
- **加一份 `scripts/check.mjs`**：启动前校验 Node 版本 ≥ 22.5、node:sqlite 可用、环境变量存在，给出友好报错。

### 5.3 产品层
- **补齐测试与监控**：当前缺自动化测试；后续可加 `vitest` 覆盖 models 层（点赞/收藏幂等、关注不可自关、评论删除权限）。
- **生产加固**：发布前设置强随机 `APP_SECRET`、为 SQLite 配置定期备份、对 Markdown 渲染加更严格的链接/HTML 安全策略。

### 5.4 协作层
- **方向确认前置**：本次用 AskUserQuestion 对齐 4 项决策非常有效，应固化为“任何开放需求先问清 4W（方向/技术/部署/交付）”的 SOP。

## 6. 可复用经验（Playbook）

> 在“受限网络 + 需可运行交付”的场景下构建全栈 Web 应用：

1. **环境先行**：校验 Node 版本与内置能力（如 node:sqlite），就近镜像，确认写入权限。
2. **选型以“可运行”为第一约束**：优先零依赖/零编译方案，把复杂度留给业务而非基础设施。
3. **分层 + 单一事实来源**：DDL、连接、仓储、格式化、认证分别成文件；schema.sql 同时被运行时与种子脚本引用。
4. **生成后必跑可观测校验**：类型检查 + 构建 + 节点_modules 体积检查，让问题在交付前现形。
5. **交付对齐评分标准**：把评分项拆成任务清单逐项闭环，并产出可追溯的 AI 日志与深度复盘。
