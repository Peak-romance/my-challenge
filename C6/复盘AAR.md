# 复盘报告（After-Action Review, AAR）

> 针对「C6 Web Application」挑战的系统性复盘：目标 → 结果 → 差异根因 → 洞察 → 改进方案。

## 1. 目标回顾

挑战要求：**构建真实可运行的产品，不是 demo**，并交付四类产物（app 链接 / demo / repo 链接 / AI 日志），按五项标准评分：

| 标准 | 权重 | 目标水位 |
| --- | --- | --- |
| productQuality 产品完成度 | 25 | 功能闭环、角色完整、体验一致 |
| technicalExecution 技术实现 | 20 | 方案合理、工程质量 |
| artifactCompleteness 产物完整性 | 15 | 齐全、可运行、可独立使用 |
| aiUsage AI 使用质量 | 20 | 恰当、有效、可追溯 |
| reflectionQuality 复盘质量 | 20 | 深入、有洞察、有改进 |

## 2. 实际结果

- 交付了**全栈「公共资产闲置平台」**：FastAPI + SQLite 后端、原生 HTML + Tailwind 前端；部门用户（发布/浏览/搜索/认领/交接单）与管理员（组织/用户/物资/日志/统计）双角色闭环。
- **91 / 91 项端到端断言通过**（`tools/smoke_test.py`）；图片真实性校验、交接单 docx/pdf 服务端导出、不可删日志留痕等“硬核”能力齐备。
- **在线 app 可访问**（verified:true），**GitHub 仓库已推送**（含 `serve.py` 单端口编排），本交付包 `D:/C6` 含完整文档与可运行源码副本。
- 过程中暴露并修复三个问题：**依赖镜像源故障**、**种子库被遗留测试数据污染**、**原启动方式不满足单端口发布约束**。

## 3. 差异与根因分析

| 预期 | 实际 | 根因 |
| --- | --- | --- |
| 依赖一次装好 | 清华镜像返回“无匹配版本”失败 | 镜像节点异常/不可达，而非依赖或版本问题 |
| 启动即规范种子 | 多出 `asset_no="2"/床` 与额外认领记录 | `database/data/app.db` 是 10/19 遗留测试数据，触发条件（用户表为空才注入）未满足 |
| 直接发布 | 原 `dev_server.py` 硬编码 127.0.0.1:3000 且前后端两进程 | 既有启动脚本面向本地双端口调试，未考虑“沙箱仅单端口 + 需读 `$PORT`”的发布约束 |

**根因归纳**
1. **环境假设未先验**：默认信任“国内镜像更快”，未先探活；把“我以前用过这个源”当成“此刻这个源可用”。
2. **种子触发条件脆弱**：`if 用户表为空才注入` 在“库已存在但脏”的情况下完全失效，缺乏“数据是否符合规范”的校验，导致遗留数据被当成正常数据。
3. **运行形态与交付形态不一致**：本地调试（双端口、回环绑定）与发布形态（单端口、0.0.0.0、读 `$PORT`）是两回事，缺一层“部署编排”的抽象。

## 4. 关键洞察

1. **“可运行”优先于“技术炫技”**：本产品用 FastAPI+SQLite+原生 HTML，零构建、零原生编译，在受限/无 Docker 环境下反而最稳——这正是对 `artifactCompleteness`（15 分）最友好的取舍。工程打分不只看复杂度，更看“拿到的东西能不能跑起来”。
2. **诊断要先验证“它现在到底在说什么”**：镜像失败时，一次 `pip install fastapi` 从官方源秒过，立刻区分“源坏了”与“包不存在”；种子异常时，一条 `SELECT` 直接看到脏数据，比猜测快得多。**可观测性（observability）是排障的第一杠杆**。
3. **触发条件要“防御脏数据”，而非仅“触发一次”**：种子机制应校验“数据是否为空且符合规范”，否则历史残留会污染 demo 与评分第一印象。
4. **部署形态应被显式建模**：`serve.py` 把“对外单端口 + 内部服务编排”单独成文件，使本地与发布共用同一入口，避免脚本分裂。
5. **评分标准本身是需求文档**：五项标准直接映射成任务清单（产品闭环 / 技术说明 / 可运行交付 / AI 日志 / 复盘），逐项对齐显著提升交付命中率。

## 5. 改进方案（可落地）

### 5.1 环境层（立即可做）
- **先探活再安装**：安装依赖前用 `pip install <任一核心包> -i <源>` 探活；国内环境优先 `https://pypi.tuna.tsinghua.edu.cn/simple` 或官方源，失败后自动切换，而非“默认一个源硬刚”。
- **固化可用源配置**：项目级 `requirements` 旁附 `.piprc`/命令模板，记录“本次验证可用源”。

### 5.2 工程层
- **种子幂等 + 校验**：`main.py` 注入前不仅判断“用户表为空”，再校验“关键表行数是否等于预期基线”；提供 `tools/reset_db.py` 一键重置为规范种子，便于复现 demo。
- **部署编排独立成模块**：`serve.py` 模式固化为本类项目的标准件（单端口 + 内部编排 + 健康检查等待）。
- **加可观测启动自检**：`serve.py` 启动后打印 `/api/health` 与首页 HTTP 状态，启动即暴露成败。
- **加一份 `scripts/check.mjs`/`.py`**：启动前校验 Python 版本、依赖齐全、端口可用，给出友好报错。

### 5.3 产品层
- **补齐自动化测试**：当前已有端到端冒烟；后续可加 `pytest` 覆盖 models 层（认领幂等、撤销数量恢复、关注/权限边界）与前端关键交互。
- **生产加固**：发布前设置强随机 `SECRET_KEY`；为 SQLite 配置定期备份；Markdown/图片渲染加更严格的链接/HTML 安全策略。

### 5.4 协作层
- **方向确认前置**：本次用 AskUserQuestion 对齐“产品取向”非常有效，应固化为“任何开放需求先问清 4W（方向/技术/部署/交付）”的 SOP——尤其当工作区已存在旧交付物时，先确认“用哪个”再动手。

## 6. 可复用经验（Playbook）

> 在“受限网络 + 需可运行交付 + 需发布/出仓库”的场景下交付全栈 Web 应用：

1. **环境先行**：校验运行时版本与内置能力，先探活镜像源，确认写入/发布权限与 Docker 可用性。
2. **选型以“可运行”为第一约束**：优先零依赖/零编译方案，把复杂度留给业务而非基础设施。
3. **数据可复现**：种子脚本幂等 + 基线校验 + 一键重置，保证 demo 与文档永远一致。
4. **部署形态显式建模**：用 `serve.py` 这类单端口编排器统一本地与发布入口。
5. **生成后必跑可观测校验**：端到端测试 + 健康检查 + 首页可达性，让问题在交付前现形。
6. **交付对齐评分标准**：把评分项拆成任务清单逐项闭环，并产出可追溯的 AI 日志与深度复盘。
