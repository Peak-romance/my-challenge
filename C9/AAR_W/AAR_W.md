## 0. 一句话结论

C8 证明"我能完成别人给定的任务（让闲置系统跑起来）"；**C9 证明"我能定义并完成自己的任务"**——从选题、拆解、实现、验收到复盘，全程自我驱动闭环。真实差异不在编码，而在三件事：**选题要自己找价值、契约要自己从代码里挖、验收标准要自己建并可证伪**。

## 1. 预期 vs 实际

- **预期**：用户一句"在 D 盘闲置平台代码里做个自驱项目"。我起初沿着"真实库存 Excel 还没上线"的线索，倾向做**批量导入**（价值最直观）。
- **实际**：与用户对齐后，选了**交互增强——资产二维码与扫码认领**。真正动手后，最大的消耗不在"写功能"，而在两处：① 把平台复制成独立产物并理解其全部约定；② 验证阶段因"误判既有契约"连吃四轮返工。
- **关键偏差**：自驱项目没有现成接口文档与评分点，**所有"既有约定"（API 字段名、返回结构、鉴权方式）都得自己读源码推断**——这是比 C8 更隐蔽的阻力。C8 至少有 README 描述接口；C9 要自己从代码挖，挖错就要返工。

## 2. 自驱项目的真实挑战（与"完成给定任务"的本质差异）

| 维度 | 完成给定任务（C8） | 自驱项目（C9） |
| --- | --- | --- |
| 任务来源 | 明确："让平台在本机跑通" | 隐含："在闲置代码里做有值的自驱项目" |

## 3. 问题解决深度（真实缺陷 → 根因 → 修复）

### 问题 1：选题定调的"方向分散"
- **现象**：勘察时发现 `闲置平台` 目录有真实库存 Excel（数百条），第一直觉是"批量导入最值钱"，但用户最终选了"扫码认领"。
- **根因**：自驱选题没有外部锚点，容易被"看起来价值最大"的线索牵引，需要先和用户对齐 + 自我判断，而非闷头做。
- **修复/应对**：用 `AskUserQuestion` 给出 3 个方向（导入 / 部署交付包 / 扫码认领）让用户拍板，把"选题价值"从主观猜测变成共同决策。

### 问题 2：后端路由漏导入 `Depends`（首轮 import 即崩）
- **现象**：`python -c "import app.main"` 报 `NameError: name 'Depends' is not defined`。
- **根因**：`qrcode.py` 用了 `Depends(get_db)` 却只在 `from fastapi import ...` 里导入了 `APIRouter/Query/Request`，漏了 `Depends`。这是新增文件时"照葫芦画瓢"漏抄一行的典型错误。
- **修复**：补 `from fastapi import APIRouter, Depends, Query, Request`，重跑 import 通过。

### 问题 3–6：验证脚本四连返工（自驱"契约误判"集中爆发）★
这是本次最有价值的复盘素材——**没有一个错误是功能逻辑错，全部是"对既有系统的假设错"**：

| 轮次 | 我的假设 | 实际契约 | 后果 |
| --- | --- | --- | --- |
| 3.1 | `/api/assets`（公开浏览）无需登录 | 实际返回 401（需登录） | 取不到资产 id，验证 0 条 |
| 3.2 | 登录响应字段是 `access_token` | 实际是 `token` | 取不到 token，无法鉴权 |
| 3.3 | `req()` 返回已解析 JSON | 实际返回原始 `bytes` | `body.get(...)` 抛 `AttributeError` |
| 3.4 | 解码块用了删除的 `np_from_bytes` | 该函数已被我清理 | `NameError` 致解码分支失效 |

- **根因（共性）**：自驱项目中，我对"平台既有约定"是**推断**而非**确认**。每一处推断都在验证时才被证伪，累计消耗约 4 轮返工。
- **修复**：逐一读 `auth.py`（确认 `token` 字段）、`routers/assets.py` 与 `deps.asset_dict`（确认字段名与列表结构）、`config.py`（确认 env 覆盖优先级），把"假设"变成"已确认的契约清单"，重跑验证 **8/8 全过**，含 opencv 真实解码出深链 `http://192.168.1.50:3000/user/asset.html?id=4`。

### 验证（闭环证据）
- `python tools/verify_qr.py` → **通过 8，失败 0**：
  - 后端启动 `/api/health=200`
  - 管理员登录成功
  - 种子资产存在（>=1）
  - 二维码接口返回 200
  - 返回内容为 PNG（魔数 `‰PNG`）
  - PNG 体积合理（>200 字节）
  - **二维码可解码且内容正确**（opencv 解码 == 目标深链）
  - 不存在资产返回 404

## 4. AI 使用反思

- **用得好**：① 用 AI 快速通读大型代码库，建立"这是一个什么平台、断点在哪"的判断；② 由 AI 编写端到端验证脚本，把"功能可用"变成可存档、可重跑的物证（含真实解码）；③ 选题阶段用 `AskUserQuestion` 把价值判断交给用户，避免自说自话。
- **用得不够 / 应改进**：我在写 `qrcode.py` 和 `labels.html` 时，**没有先让 AI 生成一份"既有契约清单"**（要复用的 API 名、返回字段、既有函数、鉴权方式），而是边写边猜、写错再查。这直接导致了问题 3 的四连返工。
- **原则提炼**：自驱项目的第一阶段应是"契约地图"，而非"直接写功能"。AI 最适合在此阶段做"既有约定盘点 + 复用点核对"，把返工前移为一步确认。

## 5. 自驱的"动力"与"阻力"（本题核心观察）

### 动力来源
1. **痛点真实且具体**：看到"实物贴码、手机扫码即达详情页"是一个可想象的闭环，动机自然，不靠意志力硬撑。
2. **成品可触摸**：二维码能真实扫出来、标签能真实打印，正反馈强。
3. **承上启下**：C8 救活了平台，C9 在上面长出新能力，有"我拥有这个项目"的连续感。

### 阻力来源
1. **选题定调消耗心力**：没有外部给定，需要在多个可能方向里判断"哪个既值又做得完"，容易被更高价值但更重的方向（批量导入）牵走。
2. **契约自挖的隐性成本**（最隐蔽）：自驱项目没有接口文档，所有"能复用什么"都要读源码确认，猜错就返工——这是 C9 相比 C8 多出来的阻力。
3. **验证边界焦虑**：前端无法浏览器级自动化，只能靠"接口实证 + 代码一致性核对"，自驱者会在"是否验证充分"上自我质疑。

### 如何化解
- 选题：用 `AskUserQuestion` 把价值判断外部化，快速收敛。
- 契约：实现前先列"复用点清单"逐一 `grep` 确认存在（已写入改进方案 1）。
- 验证：验收脚本骨架前置，功能写完即跑，反馈即时化。

## 6. 改进方案（可落地）

1. **自驱项目"契约地图"清单（立即可用）**：动手前先 `grep` 确认要复用的 API 名、返回字段、既有函数、鉴权方式，形成一张表再写代码，把返工前移为一步确认。
2. **验收脚本骨架前置**：M1 就写好 `verify_*.py` 的空壳与 AC 断言，功能每完成一块就跑，让反馈即时化（本次是功能写完才写脚本，反馈滞后）。
3. **公开接口的"最小暴露"准则**：凡因前端 `<img src>` 无法带 token 而公开的接口，内容严格限定为"无敏感的导航深链"，数据读取仍由登录守卫保护——形成可复用的安全模板。
4. **选题收敛模板**：自驱选题用三问收敛——① 真实痛点是什么？② 我能独立做完吗？③ 怎么证明做完了？三问答不出就先别动手。
5. **个人工作法**：自驱项目的"前 15%"强制花在"选题收敛 + 契约地图 + 验收骨架"，这 15% 能省掉后面约 50% 的返工。
