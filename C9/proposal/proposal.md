## 1. 一句话选题

**为 D 盘里那套"公共资产闲置平台"新增「资产二维码 · 扫码认领」能力**——管理员可批量打印带二维码的实物标签，贴到闲置资产上；现场人员用手机扫码即可在平台打开资产详情、登录后认领/查看流转。把"实物与系统脱节、现场流转靠人工登记"的痛点，变成"实物贴码、扫码即达"。

---

## 2. 项目背景（为什么这是自驱选题）

在 C8 中，我已把一个"文档声称完美、但无人跑过"的遗留全栈系统救活并验证（91/91 冒烟全过）。C9 的命题升级：**不再只是"让它跑起来"，而是"在它之上定义并完成一个有真实价值的新功能"**——这正是"自驱"的核心：选题、拆解、推进、验收、复盘全由我主导。

- **平台现状**：公共资产闲置平台（FastAPI + SQLite／原生 HTML／JWT 登录）已具备发布、认领、交接、统计的完整闭环，业务模型成熟。
- **真实断点**：资产一旦"入库"就脱离平台——实物上没有与系统关联的标识，现场盘点、领用、调拨仍靠人工记录，扫码这一环是空白。
- **数据佐证**：同一 D 盘 `闲置平台` 目录里躺着真实库存 Excel（数百条资产信息），而平台只有 3 条种子数据——"闲置"的不只是平台代码，还有大量未上线的真实资产。这让"扫码认领"不是炫技，而是对准真实流转场景的刚需增强。

---

## 3. 真实需求（Real Requirement）

> **在不动原代码的前提下，为平台新增一套"可独立运行、可演示、可验收"的二维码能力：① 单个资产二维码查看/下载；② 管理员批量生成二维码标签并 A4 打印；③ 扫码深链指向登录后的资产详情页，登录即可认领。**

它必须满足三个真实约束：
1. **不破坏原系统**：复制为独立产物（`D:\C9\artifact`），原 `D:\闲置平台代码` 零改动。
2. **可独立运行**：`start.sh` / `start.bat` 一键启动即可用，不要求 Docker。
3. **可验收**：接口级 + 解码级双重验证，扫码内容可被真实扫码器识别。

## 5. 关键设计决策（含安全权衡）

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 二维码接口是否鉴权 | **免登录公开** | 前端用 `<img src>` 直接展示 PNG，无法携带 JWT；接口仅编码"指向登录页的深链"，本身不含任何敏感数据，扫码后打开的详情页仍需登录，无越权风险。 |
| 二维码内容 | 资产详情深链 `…/user/asset.html?id=<id>` | 解耦"扫码动作"与"业务动作"：扫码只负责把人带到正确页面，认领/查看仍由既有登录守卫保护。 |
| `base` 地址 | 管理端传入 `location.origin` | 手机扫码需在"与服务平台同一可达网络"访问；用局域网 IP 打开标签页，扫码设备才能解析出可访问地址。 |
| 二维码库 | `segno`（纯 Python，无原生依赖） | 跨平台、易安装、生成标准合规 QR（任何扫码器可读），避免 `qrcode` 的 PIL 强依赖或原生编译风险。 |

## 8. 风险与应对

- **前端无法浏览器级自动化验证**（本环境无稳定 headless 浏览器）→ 以"接口解码实证 + 前端调用与既有 API/字段名一致性核对"替代，并在 AAR 中如实标注边界。
- **跨设备扫码网络可达性** → 文档与界面双提示"用局域网 IP 打开标签页"，不假设 localhost 可用。
- **公开接口的滥用风险** → 内容仅含无敏感的深链，不暴露资产数据；详情页读取仍受登录守卫保护，已在 README 明确标注。
